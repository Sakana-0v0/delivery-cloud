# del-order 服务评估报告

**服务名称**：del-order
**评估日期**：2026-08-30
**技术栈**：Spring Boot 3.x + MyBatis Plus + MySQL + Redis + RabbitMQ + Nacos

---

## 一、架构概览

### 1.1 模块构成

| 模块 | 职责 | 说明 |
|------|------|------|
| 订单主服务 | 下单、查询、取消、确认收货 | 核心业务模块 |
| 购物车模块 | 加购、删改查、清空 | 合并入同一服务，使用 Redis 存储 |
| 定时任务 | 超时取消、自动发货 | `@EnableScheduling` 驱动 |
| Outbox 中继器 | 事务性消息投递 | 定时扫描 NEW 状态行并投递到 RabbitMQ |
| 事件消费者 | 监听支付成功事件 | `PaymentResultConsumer` |

### 1.2 技术选型评价

- **MyBatis Plus**：LambdaQueryWrapper 提供类型安全的动态 SQL，选用合理
- **Redis**：购物车采用 Hash 结构存储，key = `del-cart:user:{userId}`，设计清晰
- **RabbitMQ + Outbox**：事务性发件箱模式正确解决了本地事务与消息投递的原子性问题
- **Nacos**：配置中心和注册中心的使用符合 Spring Cloud 标准实践
- **双密钥认证**：C 端/B 端分离的 JWT 池设计，分层清晰

## 二、功能性评审

### 2.1 订单核心流程

#### createOrder（OrderServiceImpl:61-118）

**正面**：
- 金额计算正确：`subtotal = price × quantity`，累加逻辑无遗漏
- 订单号、状态、时间戳设置完整
- 同一事务内写入 `t_order` + `t_order_item` + `order_outbox`

**问题**：

| 位置 | 问题描述 | 影响 |
|------|---------|------|
| 314-319 `generateOrderNo()` | 使用 `Math.random()` 生成 4 位随机数，理论并发上限 1 万/秒 | 订单号碰撞风险，秒杀场景下可能生成重复订单号 |
| 64-72 | 未对 `OrderItemReq.productPrice` 做 null 校验 | 若前端传入 null，`BigDecimal.multiply()` 抛 NPE 导致整单失败 |

**建议**：订单号生成改为 `AtomicLong` 序列或 Snowflake 算法；`productPrice` 在入参层或 service 层加判空。

#### 库存扣减 ⚠️ 缺失

`OrderMapper.decreaseStock`（18-20）有乐观锁 SQL 模板，但 **createOrder 流程中从未调用它**：

```java
// OrderMapper.java:18-20 — 已有能力，但未被使用
@Update("UPDATE t_product SET stock = stock - #{quantity} " +
        "WHERE id = #{productId} AND stock >= #{quantity} AND is_deleted = 0")
int decreaseStock(@Param("productId") Long productId, @Param("quantity") Integer quantity);
```

购物车 `addItem` 仅做内存校验，未实际扣减库存。当前实现**无法防止超卖**。在高并发下单场景下，多个用户可能购买超过实际库存的数量。

**修复建议**：在 `createOrder` 事务内对每个订单项调用 `decreaseStock`，判断返回值 `> 0` 才继续，否则抛库存不足异常。

### 2.2 订单状态机

**状态定义**（OrderStatus.java:6-13）：

| 状态名 | Code | 说明 |
|--------|------|------|
| PENDING_PAYMENT | 1 | 待支付 |
| PAID | 2 | 已支付 |
| SHIPPING | 3 | 配送中 |
| COMPLETED | 4 | 已完成（终态） |
| CANCELLED | 5 | 已取消（终态） |

**合法流转**（OrderServiceImpl:280-284）：

```
PENDING_PAYMENT(1) → PAID(2) 或 CANCELLED(5)
PAID(2)           → SHIPPING(3) 或 CANCELLED(5)
SHIPPING(3)       → COMPLETED(4) 或 CANCELLED(5)
```

**评价**：
- ✅ 状态机规则明确且集中管理（`ADMIN_TRANSITIONS` Map）
- ✅ 消费者 `PaymentResultConsumer` 有幂等保护（50-54）
- ⚠️ C 端操作（`cancelOrder`、`confirmOrder`）依赖内存状态校验，定时任务 `autoShipOrders` 直接推进状态，高并发下存在竞态风险——建议增加乐观版本号或分布式锁

### 2.3 购物车模块

**存储设计**：
- Redis Hash：Key = `del-cart:user:{userId}`，field = `productId`，value = `quantity`
- TTL：30 天

**商品信息获取**：
- 通过 Feign 调用 `ProductFeignClient` 实时获取商品快照
- `safeGetProduct` / `requireAvailableProduct` 区分了弱校验和强校验，设计合理

**问题**：

1. `del-order` 的 pom.xml 直接依赖 `del-product`（57行），但购物车需要商品信息——这是下游依赖上游的反向依赖。若未来购物车独立部署，将面临循环依赖
2. 购物车路由 `/api/v1/cart/**` 在 `SecurityConfig`（56行）中配置为 `authenticated()`，需确认 `CartController` 是否从请求中提取 `userId`（应通过 `SecurityUtil.getCurrentUserId()`，而非前端传入）

## 三、架构与设计评审

### 3.1 模块边界

**问题**：Cart 模块职责混乱
- `del-order` 同时承载订单和购物车，两者业务边界不同
- 购物车依赖 `del-product`（Feign 调用），但它们在同一个 jar 中打包，职责边界模糊
- 建议：购物车应独立为 `del-cart` 服务，通过共享 `del-common` 中的接口定义解耦

### 3.2 Outbox 模式 ✅ 实现正确

**事务保证链路**：
1. `OrderService.createOrder` 同一事务 INSERT `t_order` + INSERT `order_outbox`（NEW 状态）
2. `OrderOutboxRelay` 定时扫描 NEW 行 → `rabbitTemplate.convertAndSend` → 标记 SENT
3. 失败时增加 `retryCount` + 记录 `lastError`，保留为 NEW 供下一轮重试

**DLQ 配置**（RabbitMQConfig:63-67）：
```java
return QueueBuilder.durable(ORDER_PAID_QUEUE)
        .withArgument("x-dead-letter-exchange", PAID_DLX_EXCHANGE)
        .build();
```

**⚠️ 严重问题**：死信交换机 `PAID_DLX_EXCHANGE` 在配置中声明了，但代码中没有消费者。这意味着消息一旦进入 DLQ 将**永久丢失**，无法人工介入或告警。建议补充 DLQ 消费逻辑或接入监控告警。

### 3.3 定时任务 ⚠️ 分布式风险

**当前实现**（OrderScheduledJobs）：

| 任务 | 频率 | 职责 |
|------|------|------|
| `cancelTimeoutOrders` | 每 60 秒 | 扫描 15 分钟未支付订单，取消并回滚库存 |
| `autoShipOrders` | 每 30 秒 | 扫描支付后 30 秒未发货订单，自动进入配送中 |

**风险**：代码注释已承认（24行）：
> 分布式环境下，多副本时建议用 ShedLock 或 Redis 分布式锁防重复执行（当前为单机演示）

当前无分布式锁，多实例部署时同一订单可能被重复处理：
- `cancelTimeoutOrders`：同一订单被多次回滚库存
- `autoShipOrders`：同一订单被多次更新状态

**建议**：引入 ShedLock（基于数据库或 Redis）确保任务只在单一节点执行。

### 3.4 事务边界 ✅ 基本合理

- `createOrder`（60行）：`@Transactional`，订单 + 订单项 + outbox 同一事务
- `cancelTimeoutOrders` / `autoShipOrders`：均标注 `@Transactional`

### 5.2 安全配置 ⚠️ 需关注

**SecurityConfig（39-63）**：

| 配置项 | 当前值 | 风险 |
|--------|--------|------|

### 5.3 敏感信息 ✅ 基本合规

### 5.4 SQL 注入 ✅ 基本防护

## 八、评审结论

**del-order 服务基础架构扎实**，Outbox 事务模式、双密钥认证、状态机设计体现了良好的微服务工程实践。

当前最紧迫的三个风险依次是：

1. **库存扣减机制缺失**——这是业务正确性的底线问题，必须优先修复
2. **定时任务无分布式锁**——若服务扩容将导致订单状态错乱
3. **DLQ 无人消费**——支付成功事件丢失将影响下游服务，破坏事件链完整性

修复这三个问题后，服务的生产就绪度可提升至 4/5。
