## 二、模块 1：订单列表 + 取消 + 确认收货

### 2.1 接口清单

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 订单列表 | GET | `/api/v1/user/orders?status=&page=&size=` | 按状态分页查询 |
| 取消订单 | **PUT** | `/api/v1/user/orders/{id}/cancel` | ⚠️ 文档为 PUT |
| 确认收货 | **PUT** | `/api/v1/user/orders/{id}/confirm` | ⚠️ 文档为 PUT |

### 2.2 前端已知问题

**问题位置**：`src/api/order.ts`

```typescript
// 当前代码（错误）
export function cancelOrder(id: string) {
  return request.post(`/user/orders/${id}/cancel`) as Promise<null>
}

// 应改为
export function cancelOrder(id: string) {
  return request.put(`/user/orders/${id}/cancel`) as Promise<null>
}
```

`confirmOrder` 同理修复。

### 2.3 测试用例

| # | 场景 | 前置条件 | 预期结果 |
|---|------|---------|---------|
| 1 | 查询"全部"订单 | 已登录 | 返回所有状态订单 |
| 2 | 查询"待支付"订单 | 存在 status=1 订单 | 仅返回待支付订单 |
| 3 | 查询"待收货"订单 | 存在 status=3 订单 | 仅返回待收货订单 |
| 4 | 取消待支付订单 | 存在待支付订单 | 订单状态变为已取消（6） |
| 5 | 取消已支付订单 | 存在 status=2 订单 | 业务异常提示 |
| 6 | 确认收货 | 存在 status=3 订单 | 订单状态变为已完成（5） |
| 7 | 二次确认收货 | 已完成订单 | 业务异常提示 |

### 2.4 订单状态机

| status | 含义 | 可执行操作 |
|--------|------|-----------|
| 1 | 待支付 | 取消 |
| 2 | 已支付/待发货 | 取消（特殊业务） |
| 3 | 已发货/待收货 | 确认收货 |
| 5 | 已完成 | 评价 |
| 6 | 已取消 | - |

## 三、模块 2：评价功能（点赞/踩）

### 3.1 接口清单

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 评价开关 | GET | `/api/v1/reviews/switch` | 返回 `{praiseOpen, badOpen}` |
| 点赞/踩 | POST | `/api/v1/orders/{orderId}/items/{productId}/vote` | body: `{type: "like"/"bad"/null}` |

### 3.2 测试用例

| # | 场景 | 前置条件 | 预期结果 |
|---|------|---------|---------|
| 1 | 查询评价开关 | 无 | 返回两个 bool 字段 |
| 2 | 点赞（开关开启） | 开关 praiseOpen=true | 点赞成功，likeCount+1 |
| 3 | 点赞（开关关闭） | 开关 praiseOpen=false | 业务异常"评价已关闭" |
| 4 | 点踩 | 开关 badOpen=true | 点踩成功 |
| 5 | 点赞→点踩（切换） | 已点赞 | 切换为点踩，likeCount-1, dislikeCount+1 |
| 6 | 再次点赞（取消） | 已点赞 | 取消点赞，likeCount-1 |
| 7 | 同一订单同一商品重复投票 | - | 返回最新统计，不重复计数 |

### 3.3 UI 联调要点

- **开关关闭时**：按钮置灰，但仍可见
- **状态显示**：当前用户的投票状态（已点赞/已点踩/未投票）
- **乐观更新**：投票后立即更新 UI，失败时回滚

## 四、模块 3：支付完整流程

### 4.1 接口清单

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 创建支付 | POST | `/api/v1/payments/create` | body: `{orderNo, payMethod}` |
| 支付状态 | GET | `/api/v1/payments/{orderNo}` | 查询支付状态 |

### 4.2 测试前置条件

⚠️ **需要准备**：支付宝沙箱环境

- 沙箱 AppID
- 沙箱网关 URL：`https://openapi.alipaydev.com/gateway.do`
- 测试账号

### 4.3 测试用例

| # | 场景 | 预期结果 |
|---|------|---------|
| 1 | 创建支付宝支付订单 | 返回支付表单 URL |
| 2 | 沙箱扫码支付 | 支付成功回调 |
| 3 | 主动查询支付状态 | 返回"已支付" |
| 4 | 支付超时（订单关闭） | 业务异常 |
| 5 | 重复创建支付 | 返回原支付订单 |
| 6 | 支付回调验签 | 验签通过，更新订单状态 |

### 4.4 联调难点

⚠️ **回调地址配置**：

- 支付宝回调需要公网可访问
- 本地开发需要内网穿透（如 ngrok、cpolar）
- 或在 Nacos 配置 `pay.alipay.notify-url` 为内网地址

## 五、联调执行顺序

```

取消订单/确认收货（订单状态变更）
```

| Day 2 | 评价开关联调 | 点赞/踩联调 |
| Day 3 | 支付沙箱环境准备 | 支付联调 + 回调验证 |

## 八、风险与回滚

### 风险点

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 支付宝回调失败 | 订单状态不更新 | 启用主动轮询支付状态作为兜底 |
| 评价开关误关 | 评价功能不可用 | 临时 SQL 开启开关 |
| 订单状态机不一致 | 状态错乱 | 联调前先确认前后端状态码映射 |

### 回滚方案

所有 P1 变更仅涉及前端代码 + 后端 Nacos 配置，可通过：

1. 前端代码回滚：`git revert`
2. Nacos 配置回滚：从历史版本恢复
